# Hook-Driven tmux Agent Transport

To drive a subscription-billed CLI coding agent (Claude Code, Codex CLI) programmatically while keeping the ability for a human to attach and watch, host the CLI's ordinary **interactive** session inside tmux and get everything a controller needs — turn completion, tool calls, tool results — from the CLI's own native lifecycle hooks. Non-interactive modes (`claude -p`, `codex exec`) can bill the subscription *today* (empirically confirmed 2026-07-15 — see [`subscription-billed-programmatic-cli-agent-access`](./subscription-billed-programmatic-cli-agent-access.md)), but that access has already been shut off and restored once and is widely expected to be shut off again — it cannot be relied upon. The interactive TUI is the only subscription-billed surface with a durability track record, and that reliability — together with human-attachability and native process supervision — is the case for this architecture. Never parse the CLI's machine `--print`/stream-json protocol as the primary transport, never scrape the rendered terminal screen as the primary signal, and never depend on the CLI's on-disk transcript JSONL as a load-bearing data source.

## Architecture

1. **Interactive mode, not print mode.** Launch the CLI's normal, human-facing interactive session in a tmux pane (`claude`, `codex`, not `claude --print --input-format stream-json`). Non-interactive invocation (`claude -p`, `codex exec`) does bill the subscription as of 2026-07-15 (see [`subscription-billed-programmatic-cli-agent-access`](./subscription-billed-programmatic-cli-agent-access.md)), but it is not a surface to build on: it has already been shut off and restored once, and community expectation is that it will be shut off again. Interactive mode is the only subscription-billed surface the vendors are commercially committed to keeping open for subscribers — that reliability is the point, on top of being the only mode a human can usefully attach to (`tmux attach`; attaching to a raw JSON stream shows nothing readable) and getting native process supervision.
2. **Native hooks as the only turn-completion signal.** Wire the CLI's own hook system (Claude Code's `Stop`/`SessionEnd`; Codex's `notify=`/`hooks.*`) to a small script that reports state to the controller. Do not poll `tmux capture-pane` and pattern-match a busy/idle footer as the primary signal — that is a fallback for CLIs with no hook system, not a first choice.
3. **Native hooks as the structured-data source too.** Each CLI's `PostToolUse` hook payload carries `tool_name`, `tool_input`, **and `tool_response`** (the actual tool output/result) — first-party, documented, for both Claude Code and Codex. A hook consumer that extracts all three fields gets a full tool-call event (call + result) with no need to read the CLI's own transcript file at all.
4. **File + shell-substitution for large input, not `send-keys`.** `tmux send-keys` writes into the pane's pty via the kernel's canonical-mode line discipline, which silently drops payloads above roughly 1KB and is hard-rejected by tmux itself above roughly 8–16KB, with no error surfaced anywhere. For any prompt that might be large (a full task brief, an injected tool result, a file diff), write it to a file and let the pane's own shell perform the substitution at launch: `claude ... "$(cat prompt-file)"`. `send-keys` is safe only for short, bounded follow-ups (a few hundred bytes), sent as text and `Enter` in two separate calls with a submit-confirmed retry loop.
5. **`tmux pipe-pane` for output capture, never full stdio redirection.** Redirecting the launched command's stdout/stderr fully away from the pty (e.g. `exec cli >out 2>err <fifo`) drops the pty's kernel reference count to zero on `exec`, and tmux tears the pane (and often the whole server) down within under a second — silently orphaning the CLI process outside tmux's supervision, which defeats the entire point of hosting it in tmux. Leave stdout/stderr attached to the pty and capture with a separate `tmux pipe-pane` command instead.

## What It Enables — and What It Doesn't

This gets a controller the same event fidelity as the machine stream-json protocol (turn boundaries, tool calls, tool results, session identity) while keeping the properties that actually make tmux the right transport: a human can drop into any session and see the normal rendered UI, and the CLI's own process supervision (crash, exit, kill-session) behaves as expected because the process genuinely lives inside the pane. On subscription billing, the precise statement: non-interactive/programmatic invocation bills the subscription *today* (see [`subscription-billed-programmatic-cli-agent-access`](./subscription-billed-programmatic-cli-agent-access.md)), but that access has a revoke/restore history and is expected to be closed again — the interactive TUI hosted here is the only subscription-billed surface reliable enough to be a load-bearing dependency.

It does not give a controller a clean "cancel this turn, keep the session warm" primitive for every CLI. Interrupting Claude Code mid-turn (`SIGINT` to the pane's process) tears down the whole process, not just the in-flight turn — a fresh session is needed for the next turn, and any session-recovery design has to treat cancellation as session-ending, not turn-ending, for that CLI specifically. It also does not make the hook *events themselves* a frozen public API: both vendors document the hook event names and their fields as a supported, first-party feature, but neither commits to semver stability across CLI versions — normal changelog vigilance is required, the same posture used for any actively-evolving vendor CLI surface.

## Practical Use

- Treat the CLI's on-disk session transcript (`~/.claude/projects/.../*.jsonl`, `~/.codex/sessions/.../rollout-*.jsonl`) as a diagnostic/fallback source at most, never a primary data path. Both vendors document it as unstable: Anthropic's own hooks docs steer hook authors away from it explicitly ("written asynchronously and may lag... use `last_assistant_message` instead"), and OpenAI states outright that "the transcript format isn't a stable interface for hooks and may change over time" — there is an open, unresolved GitHub issue (`openai/codex#20952`) asking for the stability contract that does not yet exist.
- Build the hook consumer to actually extract every field the payload offers. It is easy to under-build this: at least one real, otherwise well-engineered tool (`obra/claude-session-driver`) only pulls `tool_name`/`tool_input` from `PreToolUse` and just `tool_name` from `PostToolUse`, then falls back to parsing the (unstable) transcript for tool *results* — leaving `tool_response` on the table for no platform reason, since it is present in the documented payload.
- Fall back to screen-scraping (regex on captured pane text, or a `pyte`-rendered virtual terminal) only for CLIs with no native hook system, or as a secondary confirmation signal alongside hooks. This is a real, load-bearing engineering tradeoff, not a maturity gap: broad multi-CLI orchestrators (9+ providers) lean on scraping specifically because most non-Claude/Codex CLIs lack an equivalent hook system; narrow, one-or-two-CLI tools that do have hooks available universally choose them over scraping once they graduate past a first draft.
- Split every `send-keys` text submission from its `Enter` into two calls with a short pause, and confirm the submission landed (composer cleared, or a corresponding hook event observed) before treating a send as successful — a swallowed Enter (text typed but not submitted) is a real, independently-rediscovered failure mode across unrelated implementations.
- One real tool (`kingbootoshi/codex-orchestrator`) has commit-history evidence of discovering the `send-keys` large-payload failure the hard way and switching to file-substitution afterward — a direct, independent confirmation that this is a real production failure mode, not a theoretical concern.

## Limitations

- No single real tool surveyed implements the full pattern (hooks for both turn-detection and full structured data, for both Claude Code and Codex, plus file-substitution for large input) end to end — it is a synthesis of the best-evidenced piece of each of several independent real implementations, not a single proven reference architecture. The individual pieces are each independently validated; the specific combination is not.
- Hook coverage is CLI-specific and must be re-verified per target CLI. Claude Code, Codex CLI, and (confirmed via a third tool's integration code) Kimi CLI all have real native hook systems; a CLI without one falls back to screen-scraping for both turn-detection and structured data, with materially lower fidelity.
- The `tmux send-keys` size ceiling (silent data loss above ~1KB, hard rejection above ~8–16KB) is a kernel pty canonical-mode line-discipline limit, not a tmux-specific quirk — it will reappear in any design that tries to drive a pty this way, regardless of which CLI or orchestration tool sits on top.
- Cancellation semantics are not uniform across CLIs. At least one CLI (Claude Code) tears down the whole process on interrupt rather than just the in-flight turn; do not assume a "warm session, cancel just this turn" model holds everywhere without verifying it per CLI.

## Sources

- [`kunchenguid/firstmate`](https://github.com/kunchenguid/firstmate) — production multi-agent supervisor using native per-CLI turn-end hooks (Claude `Stop`, Codex `notify=`, a Pi extension, a Grok global hook) and file+shell-substitution for large initial prompts; does not attempt structured tool-call data extraction.
- [`kingbootoshi/codex-orchestrator`](https://github.com/kingbootoshi/codex-orchestrator) — native-hook turn detection via Codex's `notify=`, with commit history (`ddc1de4`) showing an explicit switch away from `tmux send-keys` to file-substitution after hitting the large-payload failure in production; gets structured data from Codex's transcript rather than hook payloads.
- [`obra/claude-session-driver`](https://github.com/obra/claude-session-driver) — the closest real precedent to a full hooks-based design for both Claude and Codex; its `PostToolUse` handler under-extracts (`tool_name` only) and falls back to transcript parsing for tool results, which the platforms' own documented `tool_response` field makes unnecessary.
- [`smtg-ai/claude-squad`](https://github.com/smtg-ai/claude-squad) — pure interactive-mode-in-tmux with human attach, no hooks, no structured data; establishes interactive mode as the dominant real pattern.
- [`awslabs/cli-agent-orchestrator`](https://github.com/awslabs/cli-agent-orchestrator) — broad 9-provider coverage; uses hooks opportunistically where available (Claude's `PostToolUse`) and a `pyte`-rendered terminal-heuristic fallback everywhere else, illustrating the hooks-vs-scraping tradeoff as providers scale.
- [`mixpeek/amux`](https://github.com/mixpeek/amux) — independent confirmation of `tmux pipe-pane` for output capture and of splitting text/Enter sends.
- [`ogulcancelik/herdr`](https://github.com/ogulcancelik/herdr) — wires the same native hook events but deliberately discards the tool-call payload down to a coarse status label for its own sidebar UI; a real counter-example showing hook *availability* does not imply a tool captures the full payload.
- [`sipyourdrink-ltd/bernstein`](https://github.com/sipyourdrink-ltd/bernstein) — a negative case study: markets itself as a tmux-based orchestrator but its actual Claude adapter is a non-tmux `--print`/stream-json subprocess wrapper billed via `ANTHROPIC_API_KEY`. This was that project's own configuration choice (it set an API key), not evidence that non-interactive invocation forces API-key billing — `claude -p` with no key present bills the subscription just as well (see [`subscription-billed-programmatic-cli-agent-access`](./subscription-billed-programmatic-cli-agent-access.md)).
- Claude Code hooks reference (`code.claude.com/docs/en/hooks`) — documents `PostToolUse`'s `tool_response` field and explicitly recommends against depending on `transcript_path`'s contents.
- Codex CLI hooks reference (`learn.chatgpt.com/docs/hooks`) — documents `PostToolUse`'s `tool_response` field and states outright that the transcript format is not a stable interface for hooks.
- [`openai/codex#20952`](https://github.com/openai/codex/issues/20952) — open, unresolved issue requesting a stability contract for the on-disk session JSONL schema, itself confirming none currently exists.
