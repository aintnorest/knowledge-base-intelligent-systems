# Decomposed Prompting

A modular prompting architecture for solving complex tasks by breaking them into simpler sub-tasks, each handled by a specialized handler, coordinated by a high-level controller.

## Architecture Components

1. **Decomposer LLM** — Generates a structured prompting program (a sequence of sub-queries) for a complex task.
2. **Prompting Program** — A sequence of steps, each directing a sub-query to a specific sub-task handler.
3. **Sub-task Handlers** — Specialized modules or functions that handle specific types of sub-tasks (e.g., text splitting, information extraction, string concatenation, arithmetic). These can be additional LLM prompts, symbolic functions, or learned models.
4. **Controller** — Manages execution flow: task scheduling, data transfer between handlers, and status tracking.

## Advantages

- **Modularity** — Each handler can be independently optimized, debugged, and upgraded.
- **Error correction** — Error-correcting handlers can be incorporated to improve overall reliability.
- **Diverse decomposition** — Supports hierarchical and recursive decompositions, not just linear sequences.
- **Reusability** — Sub-task handlers can be shared across different tasks.

## Comparison with Least-to-Most

| Aspect | Least-to-Most | DECOMP |
|--------|---------------|--------|
| Decomposition | Linear: easy → hard sub-questions | Non-linear and recursive |

| Error correction | Limited | Built-in error-correcting mechanisms |
| Flexibility | Fixed progression | Dynamic, adaptable to task structure |

## Human-Editable Chains

Decomposition can also serve as a **human control surface**, rather than a program generated by a decomposer and executed by a controller. Expose local instructions, inputs, and outputs at each step; let a person edit intermediate data without discarding useful earlier work. A visible dependency structure shows which downstream steps consume a changed artifact. Structural edits can add, remove, reorder, or reconnect operations.

Make propagation inspectable: a local repair can change the final result in unexpected ways. Parallel paths let users compare alternative instructions or intermediate artifacts by their downstream effects, not merely inspect each step in isolation. This complements [Shared Alternatives Before Commitment](/vault/shared-alternatives-before-commitment.md); a locally good step is not necessarily globally coherent.

In a peer-reviewed **20-person** study of two short tasks, two blinded raters preferred chained final outputs in **85% and 80%** of paired comparisons. Curation accounted for **77% versus 41%** of categorized manual edits, consistent with repairing and preserving intermediate progress. These outcomes are preference and interaction evidence, not objective correctness. Completion-time differences were nonsignificant; the source's malformed time-test statistic does not justify a speed claim.

Supplied chains, extra model calls, defaults, and interface scaffolding were bundled, so the study neither isolates decomposition nor tests the model-generated controller architecture above. More stages add computational and interaction costs; users can struggle to predict propagation, and separating interdependent subproblems can lose context or coherence. Defaults may conflict with a person's mental model, while unrestricted exploration may fit a single prompt better. General authoring from scratch and equal-budget superiority remain unestablished.
