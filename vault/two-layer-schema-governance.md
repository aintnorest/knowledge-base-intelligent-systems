# Two-Layer Schema Governance

A JSON Schema attached to a model call looks like one thing: a specification. It is two. The field names, types, enums, and required-ness are an API contract that downstream code reads. The `description` strings beside them are prose that only the model reads, attached to the exact field they govern. Editing a description is prompt engineering. Editing the shape around it is a breaking change. The file does not distinguish them, so the reviewer has to.

Three terms below come from this project's prompt-maintenance practice. A **conservation ledger** is the itemized inventory a prompt restructure keeps — every normative statement, carried or moved or dropped, with a reason ([[prompt-rule-identity]]). An **emphasis budget** is the finite supply of "this one matters most" a prompt can spend: mark everything critical and nothing is. A **grain rule** constrains how large a unit an extracted value may be — one to three words rather than a lifted phrase — and exists because a downstream literal-match gate turns oversized units into forced parroting ([[gate-forced-parroting]]).

## The Pattern

1. A pipeline call declares a structured output schema. It ships in one file, versioned as one unit, reviewed as one diff.
2. **Layer 1 — the descriptions.** Every `description` is instruction text the model reads as the definition of what belongs in the field it annotates. Vendor guidance supports writing them as steering text rather than as labels, most strongly on the tool-definition side (citations below).
3. **Layer 2 — the shape.** Field names, types, enums, and required-ness are a contract. In a multi-call pipeline the consumers are concrete: workflow wiring that routes one call's output into the next call's input, fold or merge steps that key on field names, and fixtures that assert on them.
4. Because the two layers share a file, one review governs both. The result is a choice between two wrong defaults: freeze the whole file, and a high-leverage instruction channel goes unused while per-field rules are restated in prose sections that drift; or edit the whole file freely, and a wording fix renames a field and breaks a consumer two calls downstream.
5. The split, stated once, is mechanical. Descriptions may be edited without coordinating with any consumer; the shape never changes to accommodate a prompt edit.
6. The split is also checkable. A restructure that claims to have touched only descriptions can prove it: strip every `description` from both versions and compare the canonical parses — same keys, same types, same required sets, order-normalized. Compare parses rather than bytes, because a JSON reformat changes every line and nothing that matters, while a byte-identical file can still hide a semantic change under a `$ref`.

**"Freely editable" means free of consumer coordination, not free of qualification.** A description edit ships without touching wiring, folds, or fixtures — that is the whole benefit of the split. It is still a prompt edit: it changes behavior, it can regress fixtures, and it requires the same requalification any change to the prompt body does. The two freedoms are independent, and conflating them is how a "cosmetic" description edit reaches production unqualified.

## Why It Happens

Attachment is the argument for layer 1. A rule about a field, written into that field's description, is read at the point where the model is deciding what that field contains — the rule and its point of application are the same object, and cannot be separated by a later edit. A grain rule, a severity definition, or a row-shape invariant restated in a prose section two screens above the schema has two homes; one of them goes stale.

That argument is about *semantic attachment*, not token position. It is tempting to say a description is the last thing the model reads before emitting the field, or that the decoder is inside a constrained region with the description nearest to it. Neither claim is safe: serialization order within a schema object is an implementation detail, tooling reorders and canonicalizes schemas freely, and at least one vendor's structured-output implementation is documented as constrained decoding against the schema rather than as descriptive steering during generation. The attachment argument survives all of that; the positional one does not need to be made.

Layer 2 fails for a different reason: nothing reads it as prose at all. A field name is a key, and keys are matched exactly by code that has no way to guess at intent. Renaming a field or making a previously-optional one required is a change to every consumer that touches it, and the consumers are not in the file being edited. This is why "fix the wording by adjusting the shape" is the characteristic error — it is invisible in the diff under review and loud everywhere else.

The proximity that makes layer 1 useful carries an inferred hazard in one direction. An instruction executed literally costs whatever it costs, and some instructions cost more the more thinking budget the model has. A required field is not a suggestion the model weighs — it must be produced on every call, with its description sitting right beside it. That combination is fine for a format rule, and would be expected to be expensive for anything whose honest execution is an audit loop. This is a prediction from an observed failure in a neighbouring position, not something this channel has been seen to do; see the Evidence.

## How To Work With It

- Read every `description` as prompt text. It belongs in the conservation ledger, it counts against the emphasis budget, and a change to it requires the same requalification a change to the prompt body does — even though it needs no consumer coordination.
- Put a per-field format rule in that field's description, and treat the schema as the rule's home rather than a restatement of it. Where a rule genuinely needs a second home in the prompt body, state it identically in both — and back that with a mechanism, not an intention. A dual-homed rule with no parity check is a rule with a scheduled expiry date.
- Make the parity check something that runs. A test that extracts the rule's sentence from the schema description and asserts the prompt body contains it verbatim is a few lines and turns "treat divergence as a defect" from a review norm into a failing build. Where the two homes cannot be string-identical, a review checklist item naming both files is the weaker fallback; the point is that *something other than memory* notices the drift.
- Freeze the shape against prompt problems. A wording defect is never fixed by adding, renaming, or removing a field. If the fix appears to require one, either the wording is wrong or the contract genuinely changed — and a contract change is a separate unit with its consumers, wiring, and fixtures in scope.
- Make the description-only claim provable. Programmatic description-stripping plus a canonical-parse comparison turns "this restructure was cosmetic at the interface" from an assertion into a check.
- Keep out of the schema anything whose execution cost plausibly scales with the reasoning budget: self-reported counts, per-item verification tallies, "number of X you checked" fields. A required field forces the work every call. Deterministic gates downstream re-measure the same thing more cheaply and more exactly — cheaply, not free: the gate is code someone writes and runs.
- Audit the channel in both directions when a prompt reads as under-specified: rules that should be in a description are often sitting in prose, and rules that should not be in the schema at all are sometimes sitting in a required field.

## Evidence

**Vendor guidance.** Anthropic's tool-definition guidance is the strongest of the three and is unambiguous about descriptions as the steering channel: *"Provide extremely detailed descriptions. This is by far the most important factor in tool performance,"* with the list of what a description should explain including *"What each parameter means and how it affects the tool's behavior"* and the instruction to *"Aim for at least 3–4 sentences for each tool description, more if the tool is complex"* ([Define tools](https://platform.claude.com/docs/en/agents-and-tools/tool-use/define-tools)). OpenAI's structured-outputs guide makes a briefer version of the point among its schema tips — *"Create clear titles and descriptions for important keys in your structure"* — presented as a practice for maximizing generation quality ([Structured outputs](https://developers.openai.com/api/docs/guides/structured-outputs)).

The claim should not be stretched past that. Anthropic's own [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs) page does *not* recommend descriptions as a steering channel; it presents structured outputs as constrained decoding against the schema, and mentions descriptions only as where its SDK stashes constraints the supported schema subset cannot express (*"Update descriptions with constraint info (for example, 'Must be at least 100'), when the constraint is not directly supported with structured outputs"*). So: description-steering is explicitly recommended for tool input schemas, tipped for structured outputs on one vendor, and not claimed for structured outputs on the other. The practice below is consistent with that guidance; it is not fully underwritten by it.

**The pipeline.** First-party, GSL resume pipeline (`gsl` repo, `docs/resume-prompt-decisions.md`, the V2y, V2z, V3b and V3c entries, plus the standing conventions section; schemas at `parts/bundles/*/output.schema.json`). The convention is recorded as a standing rule rather than a dated ruling: *schema `description` fields are a steering channel* — per-field format rules, severity definitions, row-shape invariants, and the empty-result mitigation live in `output.schema.json` descriptions rather than being restated in prose — while *the schema's shape is a frozen contract and is never changed to accommodate a prompt edit*. Two of those terms name specific descriptions in this codebase. A **row-shape invariant** binds an output array to an input one: the auditor's `coverage` field is described as *"Exactly one row per entry in the input `terms` list, in the same order -- never more, never fewer."* The **empty-result mitigation** is the clause on its `findings` array telling the model that emptiness is an answer: *"An empty array is a valid and sometimes correct result -- emit `[]` plainly when the draft is clean rather than filling the array because the shape has room."* Both are rules about how to fill a field, written where the field is.

Four observations from the units that produced the convention:

- **The V2y restructure moved rules into layer 1 without touching layer 2.** Ledger-row semantics, the auditor's severity definitions (`blocker` / `material` / `minor`, each defined in the enum's own description), and the coverage row-shape invariant were relocated out of prose and into descriptions. The unit verified the split programmatically: stripping every `description` from the before and after schemas left them identical, so the interface every downstream consumer reads had not moved. (The check was run as a byte diff on formatting-stable files; a canonical-parse comparison is the more robust form of the same check and what this page recommends.)
- **V3b dual-homed a rule deliberately, to stop it going stale in one home.** The `terms` grain rule — short atomic vocabulary, one to three words, the posting's own spelling, never a lifted phrase — is stated in `resume_prepare`'s prompt *and* in the `terms` field description, which also carries the reason: *a downstream string-match check requires each entry literally in the finished draft, so a phrase-shaped entry forces the resume to parrot the posting.* Parity between the two homes currently rests on review discipline, not on a check that fails the build; that is the gap this page's parity-mechanism recommendation is aimed at, including for its own sibling [[gate-forced-parroting]].
- **V3c moved a live rule in and a stale rule out.** The author's `doc` description carries the document **skeleton** — the fixed section-and-slot plan the draft must fill: headline plus summary at ~65 words, a five-by-six Skills block, seven bullets on the anchor role, and so on down to the per-bullet 25-35 word range — and the superseded word-count band was deleted from it. The skeleton is the clearest case for attachment: it is a rule about the contents of exactly one field, and it now lives on that field.
- **The prevention rule cuts the other way, and is preventive rather than post-mortem.** V2z's DO-NOT-ADOPT list, still in force, forbids self-reported counts in schemas alongside inline length markers, "verify the band before finishing", and any "count" near an imperative. The mechanism is that a required field forces the count to be produced on every call. This rule was derived from the commissioned length-targeting research after a deliberation explosion — the explosion itself was caused by prompt-body and closing-block counting instructions at the recency position, not by a schema field; see [[recency-checklist-deliberation-explosion]]. No schema field has detonated in this pipeline, and none was ever allowed to hold a count, so the ban has never been tested against a counterexample.

## Limitations

- One pipeline, four schemas, one family of document-writing and auditing jobs. The governance split generalizes cleanly; the evidence for it is a single well-instrumented codebase.
- That descriptions steer is vendor-documented for tool definitions and consistent with observed compliance here. That they are the *highest-leverage* channel is an argument from attachment, not a measurement: no unit in this project moved one rule from prose to description with everything else held constant and measured the delta.
- The hazard argument — that a required field's description is the worst place for a budget-scaling instruction — is an inference from a failure that happened in a different position, in prose. It has not been observed in a schema description, and the pipeline's own ban means it never can be here.
- Per-family prompt conventions in this project differ in section wrapping — XML-tagged sections for one model family, a markdown skeleton for the other — but not in whether descriptions steer. Nothing here supports treating the channel itself as family-dependent.
- The description-stripping check proves the shape did not move. It says nothing about whether the relocated descriptions are correct; requalification against fixtures is what established that, and it found three defects the diff did not explain ([[prompt-rule-identity]]).
