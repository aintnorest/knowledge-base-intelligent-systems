# Ask or Assume? Uncertainty-Aware Clarification-Seeking in Coding Agents — Study Notes

**Authors**: Nicholas Edwards and Sebastian Schuster  
**Affiliation**: University of Vienna  
**Venue**: arXiv:2603.26233v3 [cs.CL]  
**Date**: September 7, 2026

## What It Is

A controlled study of *external uncertainty* in repository-level code repair: information missing from a user's issue, rather than information the model could discover by searching the repository. The authors place OpenHands agents on 500 synthetically underspecified SWE-bench Verified issues and compare working without the omitted facts, receiving the complete issue, being forced to ask once, and deciding during execution whether to ask. The user is a GPT-5.1 simulator holding the original issue, not a human developer.

The distinguishing design is an Intent Agent that reads the Main Agent's state history on **every turn** and emits a binary clarification-need decision. It cannot edit code; when it flags missing intent, the Main Agent must query the user before continuing. A single-agent control receives a reminder to check for underspecification on each turn. Neither uncertainty-aware variant is told upfront that the issue is incomplete; the forced-interaction baseline is told so explicitly.

## Why Mid-Trajectory Questions Matter

A missing requirement may only become apparent after opening implementation files, testing a hypothesis, or encountering a failed test. Forcing questions at the beginning can elicit generic replies or interrupt a task that is actually solvable from the repository. Never asking can turn an unspecified preference into an arbitrary code change. Separating the question decision from code execution makes the stop condition inspectable and gives the detector access to discoveries made *after* the initial prompt.

The paper uses Claude Sonnet 4.5 and Kimi K2.6, each with a maximum of 100 OpenHands iterations. The simulator answers only from the withheld full issue. The dataset was generated by GPT-4o summarization; in the authors' ten-item spot check, five summaries had genuinely indispensable facts removed and five retained enough detail to likely locate the repair. Thus asking every time would be needless even though every issue was rewritten.

## Results and Trade-Offs

| Configuration | Claude Sonnet 4.5 resolved | Kimi K2.6 resolved |
|---|---:|---:|
| Complete issue, no question | 70.8% | 72.8% |
| Hidden details, no question | 54.8% | 55.4% |
| Forced interactive baseline | 70.4% | 47.2% |
| Single agent with turn-wise reminder | 61.2% | 61.6% |
| Main Agent + Intent Agent | **69.4%** | **69.4%** |

For Claude, the multi-agent variant beats the single-agent one with reported permutation-test p < 0.001 and is not significantly different from the full-information or forced-interaction baselines. For Kimi, it also beats the single-agent variant (p < 0.001), but the gap to full information remains significant (p < 0.05). Kimi's forced-interaction result is especially poor because it sometimes used the task-completion tool instead of the question tool; the result is partly tool-instruction reliability, not simply the merits of early clarification.

The Intent Agent asked on **344/500** Claude tasks versus the forced-interaction baseline's 496/500. On the 344 it chose to ask, it resolved 65.99% versus the hidden baseline's 44.48% on *the same task subset*; on the 156 it did not ask, it resolved 76.92%, close to the hidden baseline's 77.56%. These are descriptive, selection-conditioned comparisons, not randomized proof that each question caused a fix. Claude multi-agent questions were spread across early (41.8%) and middle (43.4%) stages instead of the forced baseline's 97.6% early. Its 1,053 questions averaged 3.06 per queried task.

The price is real: Claude multi-agent API cost averages **$3.50/task**, versus $1.63 for the full-information baseline and $2.03 for the single-agent reminder. Kimi asks on **435/500** tasks and issues 3,791 questions, **8.71 per queried task**; its $1.00/task is above the Kimi full-information baseline's $0.63. Kimi's query rate is 82.99% even on the easiest (<15-minute) category. A shared architecture can therefore produce comparable repair rates but radically different interruption behavior.

## Analyst Takeaways

1. **Keep an explicit ask/proceed boundary through the whole trajectory.** An independent detector watching repository observations can catch requirements discovered after exploration; do not assume an initial clarification round is sufficient.
2. **Distinguish intent gaps from investigable code facts.** Ask a human for a genuinely missing behavioral requirement, not for a file path or diagnostic that the agent can find itself. Prefer a specific question tied to the current blocked decision.
3. **Measure both outcomes and interruption burden.** Repair rate alone masks Kimi's near-universal asking and 8.71 questions per queried issue. Track ask precision, questions per task, phase, user response quality, and spend by model.
4. **Keep the human in control of intent, not routine implementation.** The simulated-user improvement suggests useful interaction, but human time has a cost absent from the API figures; rate-limit and escalate higher-stakes assumptions rather than ask indiscriminately.
5. **Test the tool protocol.** Kimi's forced-question failures demonstrate that a clear instruction does not guarantee the model uses the actual clarification channel.

## Questions and Limitations

- The user is a cooperative oracle simulator with access to the complete issue. Real users may not know the answer, may respond ambiguously, or may be unavailable; interruption cost and answer incorporation were not established with humans.
- Automatically shortened benchmark issues can differ from natural issue reports; the authors examined only ten examples manually. The hard `>4 hours` difficulty bin has only three tasks, making its 100% ask rate weak evidence of calibration.
- Both agents in the multi-agent variant use the same frontier backbone and re-evaluate intent every turn; no cost-matched critic, event-triggered detector, or small-model monitor establishes that continuous extra inference is necessary.
- Resolution is measured through SWE-bench tests, not maintainability or whether a developer accepts the clarification and patch. The 100-iteration cap also yields lower full-information baseline numbers than published OpenHands runs with 500 iterations.
- The authors call the multi-agent behavior calibrated, but their task-difficulty and ask/no-ask analyses measure behavior, not formal probabilistic calibration or the counterfactual value of each question.
